# Разбор реальной схемы и варианты решений (2026-09-28)

Статус файла: `Новая_схема.netmap.json` появился в корне `main` (путь в
ls-tree в кавычках из-за не-ASCII имени). Числовой разбор выполнен напрямую
по `project.doc` экспорта.

## 0. Числа реальной «Усадьбы»

- 124 устройства (43 камеры, 33 other, 13 AP, 9 свитчей, 1 роутер, 5 серверов,
  9 ПК, 4 принтера, 3 POS, 4 замка), 129 связей, 6 групп, 124 порта.
- **degree GW_Usadba = 122 из 129 связей** — звезда-«волосня»: discovery
  строил FDB/ARP-линки «шлюз ↔ оконечное», хотя хинты («bridge FDB on
  2G-SW_RoomOO-1-3») говорят, что MAC выглядывает с порта в сторону свитча.
- 129/129 связей с лейблом, 111 — FDB/ARP (подтверждён спам лейблов, закрыт
  гейтом в v0.69).
- **Параллельных пар нет вообще** (все пары = 1 линк) — «рамки» на скрине не
  веер параллелей, а ортогональные обходы длинных GW↔endpoint рёбер.
- Ширины групп: 1974/1834/2224/7164/2114/**12504** px — подтверждает
  компактную пилюлю ≤380px (v0.69).
- 106 из 109 оконечных имеют ровно один хаб-сосед (GW) → фасовка v0.68 на
  обзоре сворачивает их в счётчики; /24: 10.11.5×50, 10.11.99×35,
  192.168.11×29, 192.168.3×8, 10.11.40×2; локаций нет (стратегия «локации»
  честно пустая, гибрид группирует по /24).
- В доке есть мусорное устройство-«свитч» с именем из «+» (артефакт
  discovery) и хинты-порты без узнаваемого свитча (sfp1-SW-OPT, 5G,
  ether*-srv*) — авто-ремонт по имени на этом файле переставляет 2 связи
  (цепочка SW_RoomOO); остальное чинится сканированием самих свитчей по
  SNMP (их собственный FDB даст честные L2-линки) — рекомендация пользователю.

## 1. Что видно на скринах (симптомы)

1. Ближний зум: рёбра-«ленты» толщиной в десятки px (stroke масштабировался
   с зумом); сотни синих пилюль-лейблов «bridge FDB on … (ARP …)» на каждом
   кабеле; розовые «рамки» — веер параллельных кабелей с офсетом ±сотни px;
   карточки устройств при этом читаются нормально.
2. Общий план: почти пустое поле с несколькими растянутыми «полосами» —
   пилюли групп наследовали ширину рамки (тысячи px), состав фасован внутрь.
3. Данные реальной сети: несколько /24 (10.11.40.x, 192.168.11.x), FDB/ARP-
   хинты discovery в `link.label`, мульти-пары хаб↔хаб с десятками линков,
   оконечные без локаций (SALTO/AGAT/Canon/PC-…).

## 2. Что уже закрыто правилами (v0.67–v0.69, см. display-logic.md)

| Симптом | Решение | Релиз |
|---|---|---|
| «мёртвые» стратегии на сгруппированной карте | takeover-перегруппировка + `userGroupId` + restore | v0.67 |
| портовые якоря = до 57% DOM | якоря только near/selected/hover | v0.67 |
| разрозненные эвристики видимости | контракт сцены `scenePlan.ts` | v0.68 |
| пустой обзор | пилюли групп + фасовка + пучки ×N на far | v0.68 |

| «рамки» веера | `fanOffset` ±42px; пары >6 → пучок ×N | v0.69 |
| сотни лейблов | лейблы только на активных рёбрах / тумблер | v0.69 |
| полосы-пилюли | компактная пилюля ≤380px | v0.69 |

## 3. Как это делают похожие продукты

Отрасль решает ту же задачу («hairball» больших сетей) набором приёмов,
который у нас реализован частично:

- **yFiles** (эталонная SDK-практика): progressive disclosure — стартовое
  представление 20–50 узлов, раскрытие соседей по запросу; сворачивание
  подструктур; level-of-detail по зуму; edge bundling — родственные рёбра
  идут общими коридорами, паттерн связности читается вместо «частокола»;
  заявлена плавность на 50 000+ узлов за счёт LOD и виртуального вьюпорта
  ([1](https://www.yfiles.com/faq), [2](https://www.yfiles.com/the-yfiles-sdk/features));
  в 3.1 — быстрый edge-path bundling и LOD-фейдинг лейблов
  ([3](https://www.yfiles.com/the-yfiles-sdk/web/yfiles-for-html/version-31)).
- **Auvik / Domotz** (MSP-сегмент): непрерывно обновляемая живая топология,
  свернутые сайты/сегменты, детализация по клику — карта как навигатор,
  а не чертёж ([4](https://blog.domotz.com/all/network-diagram-software/),
  [5](https://wifitalents.com/best/network-topology-mapping-software/)).
- **SolarWinds Network Topology Mapper**: автопостроение L2/L3-видов из
  discovery, экспорт в Visio — сильная сторона «документационный» контур
  ([6](https://gitnux.org/best/network-topology-software/)).
- **NetBrain**: динамические карты под задачу (troubleshooting-вид строится
  от точки интереса, а не «вся сеть сразу»).
- **PRTG Network Atlas**: карта = вид мониторинга, статусные цвета вместо
  подписей на рёбрах.

Общий знаменатель хорошего UX на больших сетях: **карта стартует сжатым
представлением и раскрывается по интересу пользователя**; рёбра
агрегируются/бандлятся; подписи живут в LOD, а не на каждом ребре.

## 4. Варианты следующих шагов (приоритет по пользе/цене)

0. **Ремонт звезды FDB** — РЕАЛИЗОВАНО в v0.70: `src/topoRepair.ts`
   (консервативный план: конец связи со шлюза → на свитч, узнаваемый в
   хинте; без дублей; откат Ctrl+Z), пункт «Вид → Починить связи по
   FDB-хинтам» с dry-run подтверждением; та же эвристика в
   `electron/discovery.cjs` на этапе сканирования. На реальном файле —
   2 связи (SW_RoomOO); полнота придёт со сканированием свитчей по SNMP.
1. **Minimap + «стартовое представление»** (RF `<MiniMap/>` + открывать
   большие карты в режиме обзора с пилюлями, нырок двойным кликом).
   Дёшево, сразу даёт навигацию по реальной схеме. ≈ v0.71.
2. **Focus-first режим** (NetBrain/yFiles): кнопка «показать окрестности» —
   старт с ядра и 1-2 колец соседей, раскрытие по клику (progressive
   disclosure 20–50 узлов). Средней сложности: нужен режим «видимой
   подграф-проекции» в scenePlan.
3. **Геометрический edge bundling межхабных коридоров** (yFiles-style):
   пары «звезда вокруг ядра» ведут общие коридоры; у нас уже есть агрегация
   >6 и fan-cap, дальше — только если на реальном файле останется hairball.
4. **LOD-фейдинг лейблов вместо бинарного гейта** (плавное появление
   подписей на near, как WebGL label fading в yFiles 3.1) — косметика.
5. **Heatmap проблемности** (yFiles 3.1 heatmap): подкраска хабов по числу
   down-оконечных/алертов — полезно для MSP-взгляда, дёшево поверх
   существующих liveStatus.

Рекомендация: начать с **1 + 5** (навигация + проблемность) — оба малые и
закрывают главную боль реальной схемы «где я и что болит»; **2** — следующим
релизом как системное решение «вся сеть сразу не нужна».
